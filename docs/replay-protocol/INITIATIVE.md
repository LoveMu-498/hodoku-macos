## 倡议目的

双方持续扩充赛事回放时，既有二进制文件头相同，叠加标记的字段和含义仍可能冲突。希望双方共用一份可审阅、可演进、可测试的协议，减少“能打开但画错”“另存后丢失证据”等问题。这里的赛事回放是一次解题的记录，不扩充比赛管理功能。

这次提交的是协议与流程倡议，不是要求 Windows 直接采用 Mac 的实现、快捷键或全部功能。请重点确认两件事：**是否理解并愿意支持共同维护规则；取得协议、提交修改、接收确认的流程是否在 Windows 实际环境中打通。**

## 双方必须落实的维护规则

1. 任何影响回放记录、编码、解码、显示、另存、历史分支的变化，实施前必须检查共同协议及本端能力档案。
2. 与已确认协议一致的更新，沿用对应协议版本，补充相关验收。新功能可以保持本端专属，但不能破坏共同核心或默默改变既有共享字段含义。
3. 不符合现行共同协议的更新，必须先提出协议修订，写清字段、语义、旧端处理、损失、迁移和样例。首选向上述 GitHub 仓库提交协议更新 PR；不能访问 GitHub 时必须回传同样内容的离线提案，由 Mac 维护方代录入。传输困难不能成为跳过协议的理由。
4. 两端均有提案权。共享规范的修改须有两端明确审阅记录；一端合并或发布代码不等于另一端已经兼容。规范通过与各端能力通过分别记录。
5. 读者能力先部署，再启用新写出格式。会让旧端读错、误画或误解的重要新语义，必须选择新标签／新语义版本，并在必要时提升容器版本；不能以“文件头还是 v3”宣称无破坏。
6. 不支持的可选显示数据可保留原文、说明未显示；不能把假叉画成真圈，不能把旧色组或 RGB 颜色当作逻辑覆盖证明。旧端无法安全解释的重要内容必须明确拒绝或使用声明有损的兼容导出。

**请双方把以上规则落实到各自项目的 `AGENTS.md` 或等效、每次开发确实会加载的持久指令文件。只在聊天中表示理解不算落实。** 若还采用记忆，记忆只记录固定协议入口与检查责任，正式规则仍以版本化文档为准。Mac 已在本地项目指令中加入这一门禁；Windows 请返回文件路径、实际新增条款、对应源码版本，并用一次新任务证明该条款会被读取。

建议落地条款（双方按实际项目路径替换）：

> 修改赛事回放前，读取共同协议入口、固定版本与本端能力档案。对格式、语义或保留行为的差异，先提交协议修订提案及兼容测试；GitHub 不通时交付带基线哈希的离线提案并等待确认。未经共同确认不得改变既有共享字段含义；未实测的功能不得标记兼容。实现、发布、提交及联系仍遵循本项目授权边界。

## 正式入口与替代传递

暂定 GitHub 主入口：[LoveMu-498/hodoku-macos](https://github.com/LoveMu-498/hodoku-macos)，协议路径 `docs/replay-protocol/`。**当前为草稿候选，主分支尚未正式采用；请使用交付方提供的真实草稿 PR 与固定 commit 入口，不把 main 的目标路径当作已经发布。** 首次可用本包完成接收与离线回传；草稿入口可达后仍须测试真正的读取与 PR 提交通道。

GitHub 通道：取得固定 commit 的协议 → 创建一次最小协议文字修订 PR → Mac 审阅并返回提案编号、意见与版本 → Windows 再取得确认后的内容并核对哈希。PR 可在双方同意后作为纯流程验证关闭，不必改动解题逻辑。公开仓库可读取不表示 Windows 能登录、fork、push 或创建 PR，这些必须分别验证。

离线通道：Mac 导出固定基线及 SHA-256 清单 → Windows 校验、填写回执并附协议修改补丁 → 通过双方已能使用的文件传递渠道回传 → Mac 校验基线、检查补丁、明确返回接收／待修改／不接受及原因 → Windows 收到确认并核对提案编号与哈希。Mac 在已有发布授权时才代录 GitHub，并把真实 PR 链接回传；不能静默修改对方提案。离线沟通结果不会因为尚未上传而丢失。

将来如使用本地服务器，它只能先作为带版本与哈希的镜像或传递入口；应另测 Windows 网络可达性、上传权限、持久保存和确认回传。双方明确变更权威之前，不出现 GitHub 与本地服务器同时可编辑却相互冲突的两个主版本。

## 首次共同验收：请实际执行，不能只口头确认

使用 [WINDOWS-RECEIPT.md](WINDOWS-RECEIPT.md) 回传结果，至少完成：

1. **取得**：解压本交接包、验证清单，记录协议编号与 SPEC.md 的 SHA-256。再试 GitHub 读访问；失败记录准确时间、操作和错误，不提供 token 或密码。
2. **落实**：将维护条款写入 Windows 的持久项目指令，给出相对路径和条款；开启一次新的开发任务，确认其实际读取到条款。
3. **提出**：做一次不会改变算法的最小文字修订，按提案模板提交 PR。失败则附 `changes.patch` 或明确的前／后文本走离线回传，必须带基线哈希。正文指出这是流程演练。
4. **接收与反馈**：Mac 对这个真实回传核验、审阅并返回确认文件；Windows 再确认收到、编号一致和哈希一致。仅发出邮件、文件或 PR 不算完成往返。
5. **格式后续验收**：取得新版 Windows 固定源码与合成回放样例，验证 Mac→Windows→Mac 和 Windows→Mac→Windows 的共同字段、语义展示及约定损失。传递通道通过不等于回放内容已经兼容。

验收状态必须分开：`未执行`、`失败`、`已验证`，并注明执行端、版本、渠道、证据。GitHub 流程与离线流程分别标记；Windows 不能访问 GitHub、但真实离线往返已通过时，可以确认离线协作已通，GitHub 路径仍是失败或待验证。

## 本次格式建议需要先澄清的事项

- 已有 O6 使用整数像素坐标；附件 O10 改为标准圈叉和归一化坐标。当前 Mac 会拒绝 O10，固定旧 Windows 可能把新字段当旧坐标误画。因此这是实质兼容变更，不能仅凭 v3 不变判定安全。建议先登记实际部署的变体、为其做明确导入适配，未来冻结旧标签并以新标签扩展。
- `MT 1` 是显示状态，不能单独证明某候选必真／必删。共同结果需要分支前提、覆盖资格、结果方向及历史依据；建议保存当时结果，不依赖观看端的新求解算法重新生成旧结论。若只有显示开关，先按不支持的显示状态处理。
- 多个假设分支共同推出 C，只能在其前提覆盖全部允许情形且各分支推导成立时推出无条件 C。两个真圈色组的交集本身不是覆盖证明。例如同格候选 {1,2,3} 只比较“填1”“填2”两分支，不能忽略“填3”。
- 数字版本 <=3 不自动代表同一格式族；v3 的 methodStep 处于盘面字节前，不能任意忽略字节。旧 Mac 退役格式不会因这份倡议被承诺恢复支持。
