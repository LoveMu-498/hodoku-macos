Status: proposed; bilateral acceptance pending

## 三层边界

| 层 | 管什么 | 演进边界 |
| --- | --- | --- |
| 共同容器 | 字段顺序、编码、帧、盘面、时间 | 破坏布局或安全读取时升级容器主版本 |
| 共同语义与能力 | 标记含义、位置、阶段、未知数据和损失 | 新能力登记新标签／显式语义版本，旧标签含义冻结 |
| 平台扩展 | 本端完整证明、恢复、精确涂鸦等 | 平台独立版本；不能改写共同核心，丢失必须声明 |

应用版本、容器版本、协议修订号、平台扩展版本分别记录。候选规范编号不写入现有 hrep，不声称当前读取器具备能力协商；文件内能力声明的载体须作为独立提案通过后才能启用。

## 已核实共同容器基线

两端被检查的源码使用 HRPL `0x4852504C`，版本 3。大端 Java DataOutputStream；UTF 是 modified UTF-8，按编码字节限制到 65535，不是通用 UTF-8 文件。

依次：magic:int、version:int、id:UTF、startedAt/elapsedMillis/endedAt:long、completed:boolean、frameCount:int。

每帧依次：operationId/wallTimeMillis/elapsedMillis:long、label:UTF、overlayData:UTF、methodStep:boolean；然后 81 格各 value:byte、fixed:boolean、candidates:short、userCandidates:short。行列位置用格索引 0..80，候选 atom=cell*10+digit，digit=1..9。

现有 Mac 明确只接本格式族 v3，不支持已退役的旧 Mac 外壳。版本支持范围必须逐项列出；不能用版本整数大小替代格式定义。Mac 私有尾扩展及完整字段见 ../replay-file-format.md；本候选规范不要求 Windows 执行私有证明。

## 共同语义候选要求

- 盘面是当时真实状态；历史已删候选可以只读高亮，不能恢复为盘面候选。原始输入、证据展示、应用后盘面要区分，不能凭颜色把历史步骤变成可执行对象。
- 时间区分真实记录时刻、有效解题用时、播放器停留时长。事件顺序与操作组身份保留；不得在导入时补造不存在的初始状态或操作。
- 格／候选位置用语义锚点；自由几何坐标必须声明像素或归一化、参照空间和大小。RGB/ARGB 是外观，色组身份与圈真／叉假、起点、待接纳结论分别表达。
- 单色多个起点是至少一个为真还是每个均真，必须明确。多分支共同结果必须保存覆盖前提、结果真／假方向与来源；中间推导是否机器验证另外标记。MT 开关不能替代这些证据。
- 应保存用于历史展示的冻结结论，不以新版本求解器在观看时重算后覆盖历史。允许独立验证或补充说明，须明确区分。

## 标签登记与现状

| 标签／变体 | 已核实或报告的身份 | 候选治理要求 |
| --- | --- | --- |
| B、G/R/C、链标签、K/M | 当前共同前缀 | 定义字段、范围、颜色角色和重复处理；保留现有语义 |
| P、O6 | 固定参考中的整数像素涂鸦／圆 | 冻结旧含义；缺少参照画布不能猜测定位 |
| O10 | Windows 新建议稿报告的圈叉＋归一化坐标 | 新源码／样例待核实；单列变体，不叫无破坏扩展 |
| MT | 建议稿报告的多色组显示开关 | 不当作已证明结论；是否共享、如何冻结结果待共同确认 |
| DM1、DT、PF1 | 当前 Mac 写出的可选坐标、操作与鳍角色 | Windows 理解／展示／保留能力分别声明，不宣称共同采纳 |

未来注册项必须包含标签、精确字段数量、类型、范围、语义、版本、必要性、未知处理、降级、样例、提出端与确认记录。已部署但未登记变体按明确的遗留兼容规则处理，不以 >=字段数猜测所有未来版本。

## 兼容能力分别声明

每端能力档案填写固定源码版本、协议基线和每项能力：读取、正确展示、另存保留、编辑后保留、从帧开始解题。只支持读取不能标记完整兼容。

未知的可选标签保留原始行和顺序，不执行；已知标签损坏严格处理，不能伪装成未知。无能力显示时说明未显示，不能反转真／假含义。允许丢失的平台扩展须列清单并在对应能力档案声明。

必须理解的重要新语义，不能仅在 v3 中新增一个旧端会忽略的 required 标记来保证安全；旧客户端不会因此自动拒绝。需要通过已升级读取器的受控过渡、新容器版本，或明确有损的兼容导出保护。

读取限额、边界和畸形输入作为共享安全基线另行确认；提案至少覆盖非法格／数字、非有限几何值、错误帧顺序、未知必要版本、UTF 溢出、截断与过大文件。不能静默截断或覆盖上次成功文件。

## 修订与验收

两端遵循 CHANGE-PROPOSAL.md；GitHub 与离线采用相同基线及哈希。提案、接受的规范、各端完成实现、各端通过验收分别记状态。

对每个已接受能力至少有合成文件和预期语义，并验证两种方向的读写往返、旧端行为、未知数据保留、不同窗口大小显示，以及分支不会执行历史证据。编辑重录与直接另存分开测。比较共同数据及声明允许丢失的平台内容，不强求同一字体或像素图。

先通过取得与提交确认的真实通道演练，再逐项扩大共同能力。本候选规范不是当前所有要求已实现的证明。
