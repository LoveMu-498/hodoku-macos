# 两至三次交接确定首版协议

本规则落实用户 2026-10-05 的目标：第一轮给出可直接接受的初版；第二轮返回明确决策及完整反提案；第三轮只确认准确版本或报告真正阻碍。目标不是反复转述双方 AI 的建议。

## 同一工作入口

当前使用 [协议草稿 PR](https://github.com/LoveMu-498/hodoku-macos/pull/2)。两端 AI 在各自团队授权与可用账号范围内直接读取同一 PR、提交协议修订或回执。人的首次工作是把任务与授权交给本端 AI；常规字段审阅、修订和确认由 AI 在共享入口处理。

共享入口不会自动唤醒对方 AI。双方持久开发指令要求在回放任务开始时检查最新已确认版本和相关未结提案；需要持续监听时，由团队另行提供常驻执行环境和明确授权，不能声称仅创建 PR 就已有后台协作。

## 三次交接的明确产物

| 交接 | 发送方 | 必须交付 | 收敛条件 |
| --- | --- | --- | --- |
| 1 | Mac → Windows | SPEC 固定版本和哈希、默认决策、实际可用样例、Windows 执行任务与回执模板 | 对方可以直接审阅、校验并回答，不以“请再给建议”作为任务 |
| 2 | Windows → Mac | 逐项 ACK／AMEND／BLOCK、真实渠道结果、持久指令落实；AMEND 必须附完整补丁／最终文件、候选哈希与接受声明 | ACK 精确指向原版；AMEND 表示 Windows 接受自己提交的准确候选，并说明是在维护团队何种授权下作出 |
| 3 | Mac → Windows | 接受准确候选并写同哈希 ACK，或仅处理剩余必需冲突并报告 BLOCK | 两端接受同一候选哈希，即可冻结首版；不要求对方再复述一次已经明确接受的内容 |

第二轮全部 ACK 时，双方规范一致已可确定，第三次可只发送冻结记录。第二轮返回完整 AMEND 且 Mac 接受它时，Windows 对其候选的接受与 Mac 第三轮 ACK 已指向同一内容，不需要第四次技术确认。

Mac 第三轮若又改变了对方未预先接受的内容，不能声称已确定。只能采用第二轮明确授权的具体替代方案、冻结不受争议影响的基线，或把必需冲突一次性交开发团队解决。不能把条件接受解释成无限制授权。

## 可直接采用的默认决策

- 首版编号为 `HRPL-COMMON-1.0`；确认状态单独记录。候选文件具有该编号不表示已确认。
- 冻结范围为 SPEC 的共同 v3 容器、基础语义、旧标签不可改义、能力／损失分别声明、共同修订及真实通道规则。应用版本、容器版本与协议编号分开。
- O10、MT、完整原生证明等尚未共同核实能力按登记的遗留／可选扩展处理；不把它们宣称为已跨端实现。可选能力未实现不阻止确认基础协议；实际不能读取某类文件的端不能宣称该类文件兼容。
- 技术细节有安全明确的默认方案时，AI 直接决定并记录依据；反对默认方案必须给可实施替代文字、受影响字段及实际证据。不得只返回笼统建议或把普通技术选择再交给人类转述。
- GitHub 可用时直接在共同入口交互；GitHub 不通时第一轮必须登记一个双方可用的直接文件入口。微信等仅能由人转发的渠道属于临时降级，不能算“AI 直接持续协作”已实现。

产品原生功能保持优先。共同基础为看重要历史画面和从真实快照进入棋盘；理解全部技巧、执行历史证明和编辑所有外端标注属于可选能力。原生功能扩展优先由记录适配和通用显示／原生扩展承载，不用最小共同能力压缩产品功能。

## 统一回传记录

每次记录：exchange_id、round、sender、team_authorization、baseline_spec_sha256、candidate_spec_sha256、candidate_commit／候选包编号、candidate_contract_sha256s、decision、accepted_scope、amendments、blockers、evidence、channel。decision 为 ACK／AMEND／BLOCK；AMEND 必须说明接受其准确候选还是仅为未确认建议。

有效确认必须来自维护团队或其已授权 AI，哈希只保证内容一致，不证明授权或身份。记录可以是回执 Markdown，也可附相同字段的 JSON；不要求改现有 hrep。

确认的规范内容包括 SPEC.md、CONVERGENCE.md、INITIATIVE.md，必须固定这三份文件的完整哈希清单；GitHub 候选另固定 commit，离线候选另固定包编号。提案／回执／提示词模板与能力表是操作材料，其变化不能替代或改变已冻结规范。确认标准为：两个真实参与端有权接受、针对同一准确规范文件哈希清单、接受范围一致、必需条款无 BLOCK。只有 SPEC 哈希一致、治理内容却不同，不足以确认。规范确认、GitHub 合并、实现能力验收、持续协作通道四项分别记状态。没有合并授权时，已确认规范也可先引用固定 commit 与确认记录；不得自行合并 PR。

## 更新与真正阻碍

后续更新沿用相同提案编号／基线哈希、ACK／AMEND／BLOCK 与确认标准。两端 AI 在预先明确的“协议文档及合成验收材料”委托范围内直接维护；应用代码、发布、网络／密钥变更和超范围事项仍遵守团队授权。

遇到缺少访问工具、凭据授权、直接共享入口、准确格式事实或必需语义冲突时，暂停依赖步骤并向本端开发团队报告：具体阻碍、尝试与证据、影响、最小所需处理、可继续工作。不能伪造 ACK、把未回复视为同意，或为了限制轮数掩盖冲突。

两至三次是收敛预算，不是对网络、外部回复或未知实现的保证。用足预算后仍有必需 BLOCK，结果必须为“未确定＋具体阻碍”，而不是再发一轮泛泛征询。
