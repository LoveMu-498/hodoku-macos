# 开源与发布约定

维护约定：明确项目来源、保留许可和修改日期；
使用、修改、商用与再分发按原许可证处理，不增加用途限制。
主应用 GPL-3.0-or-later，独立组件保留自己的许可。本项目是非官方 macOS 修改版。

## 三种交付内容

| 内容 | 普通 Git 提交 | GitHub Release | 本地完整分享包 |
| --- | --- | --- | --- |
| 应用源码、资源、必要构建脚本、COPYING/来源/修改说明 | 是 | 对应版本的源码归档 | 包含 |
| App 内置 Java | 否 | DMG 中保留，用户无需另装 Java | app 中保留 |
| Java 完整对应源码与构建材料 | 否 | 单独附件，与 DMG 同时可取、明确对应 | 与 app 一起附带 |
| 构建缓存、安装备份、个人设置、内部日志 | 否 | 否 | 不附个人数据 |

GitHub [大文件说明](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)
建议用 Release 分发大文件，普通 Git 拒收超过 100 MiB 的文件。把 Java 材料单独提交为
另一个大文件 Git commit 不能解决仓库膨胀，应使用附件。只公开源码、不发二进制时，不必
为了源码仓库而上传 Java 运行时大文件；未来发布含 Java 的包时仍要履行其条件。

## 本次必须主动提醒的禁止事项

- 不删除/替换上游及后续贡献者版权、许可、无担保声明，不称整个程序为自己的原创。
- 不将继承的 GPL 应用整体换成 MIT、闭源或“仅限非商业”；不剥夺接收者的 GPL 权利。
- 不只发修改版二进制，却仅提供旧上游源码、一个 diff 或不匹配的源码 tag。
- 不把 Java 的 Classpath Exception 当作免除 Java 分发义务；分开上传不等于可以省略。
- 不将 GPL 软件许可套用到另有 GNU FDL 等许可的网站文章、图片及其他素材。
- 不把收到回复、未收到回复、GitHub fork 数量或技术测试通过当作全部许可已审查的证明。

以上依据：[GPLv3 §4–6、§10](https://www.gnu.org/licenses/gpl-3.0.html)、
[上游软件/网页许可](https://hodoku.sourceforge.net/en/index.php)、
[Adoptium 许可说明](https://adoptium.net/docs/faq)。

## 执行停点

1. 核对当前 macOS 源码的版权声明、来源和修改记录，只公开本项目必要文件。
2. 准备公开源码文件清单，检查工作区与历史中的个人路径/日志/凭据；保留本地文件，不自动重写历史。
3. 按本次产物验证构建与对应源码。技术通过、来源核查和分发材料完整性分别记录。
4. 准备上游联系草稿、拟发布文件与 Release 说明供审阅。发布和联系消息分别遵循维护者授权。
5. 真正发布时提供明确源码 commit/tag、日期、架构/系统范围、校验值和 Java 对应源码附件。

GPL 已提供满足条件时的发布授权，联系上游用于感谢、准确署名与贡献合作，不把逐次请示
作为许可证未要求的前置步骤。公开链接可直接用于咨询上游；联系草稿保留在本地，不作为软件源码的一部分发布。

## 版本推进与密钥保护

- 唯一版本来源为 `src/version.properties`；应用 About、Info.plist、DMG 文件名和 tag 保持一致。
- 每次发行更新 CHANGES.md，记录日期、实际源码 commit、校验值和验证范围。
- 后续只有用户明确要求更新 GitHub/发布时才提交、推送或创建新 Release；本地修改不自动推进远端。
- 公开集合采用白名单，并扫描 API key、访问令牌、私钥、密码、个人路径及配置；扫描输出仅记录位置，不打印密钥。
- Git 历史、内部研究记录、缓存与另一套项目不进入本次首次公开仓库。保留本地原文件和历史。
- 二进制发布必须从对应的已提交源码构建。Java 对应源码附件与 DMG 同次提供，遵守其原许可证。
